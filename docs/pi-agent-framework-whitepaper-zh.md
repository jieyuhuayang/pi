# pi Agent 框架运作原理白皮书

**面向 AI 产品经理的系统性深度解读**

> 本文基于 pi monorepo（earendil-works/pi，v0.84.x）源码与官方文档写成，所有机制描述与数字均可在文中标注的源码路径中查证。

## 摘要（Executive Summary）

pi 是一个开源的终端编码 Agent 及其底层框架（作者称之为 harness，"缰绳/挽具"，即包住大模型、让它能安全做事的运行时外壳）。它对"Agent 框架应该长什么样"给出了一个与主流方案几乎相反的回答：**把内核做到最小——默认只给模型 4 个工具、一份 169 行代码生成的系统提示；把其余一切能力做成可插拔的扩展资源；并让 Agent 自己成为扩展的作者**。

理解 pi 的价值不在于"要不要用 pi"，而在于它以最小的体积暴露了任何 Agent 产品都绕不开的五个根本问题及其一种完整解法：

1. **怎么执行**——一个"双层循环 + 事件流"的执行引擎：每个回合（turn）就是一次大模型调用加上它触发的工具执行，循环往复直到模型不再要求调用工具；
2. **怎么接模型**——一个把 30 多家模型服务商归一成约 10 种 API 形态的统一模型层，模型与对话上下文都是可序列化的纯数据，中途换模型不丢历史；
3. **怎么记忆**——会话不是一条消息数组，而是一棵可原地分支的树；上下文超限时自动压缩成结构化摘要，完整历史永不丢失；
4. **怎么扩展**——扩展（Extensions）、技能（Skills）、提示模板、主题四类资源加上打包分发机制；系统提示里内嵌了 pi 自身文档的路径，模型可以读自己的手册、给自己写插件；
5. **怎么可靠可控**——通过 steering 消息队列和工具调用拦截实现人机协同（Human-in-the-loop），通过会话树实现线程级持久化，通过重试与崩溃恢复规范逼近可恢复执行。

如果你熟悉 LangGraph，可以这样把握两者的根本分野：**LangGraph 把控制流显式建模为图（节点、边、检查点），pi 把控制流固化为一个循环，把所有的"变化"推到数据（会话树）与钩子（扩展事件）里**。第八章将逐项对照 LangGraph 的 Human-in-the-loop、持久化与持久化执行三大特性在 pi 中的对应实现。

## 一、为什么产品经理需要理解 Agent 框架

**本章结论：模型决定 Agent 的智力上限，而 harness 决定智力能否兑现为可交付的产品能力；pi 是市面上最适合用来"解剖"这层结构的标本。**

一个 Agent 产品由三层构成：底层的大模型（提供推理能力）、中间的运行时框架/harness（提供执行循环、工具、记忆、恢复能力）、上层的产品交互（UI、权限、协作流程）。产品经理通常聚焦第三层，但第二层的设计决策——工具怎么给、上下文怎么管、失败怎么处理、人怎么介入——直接决定了产品体验的天花板：为什么 Agent 会"忘事"？为什么长任务会中途崩掉回不来？为什么加一个功能要改内核？这些问题的答案都在 harness 层。

选 pi 作为解剖标本有三个理由：

- **结构最小**。pi 刻意不做子 Agent、不做计划模式、不做权限弹窗、不做 MCP（Model Context Protocol，模型上下文协议）——这些"减法"使得剩下的部分恰好就是一个 Agent 框架不可再省的骨架。
- **决策显式**。每一个"不做"都在 README 中给出了理由和替代路径，每一个默认值（压缩阈值、截断上限、重试次数）都能在源码中找到注释说明。
- **文档完备**。仅扩展系统一份文档就超过 3000 行，且文档本身就是产品机制的一部分（后文详述）。

本文按上述"五个根本问题"组织第四到第八章——这不是 pi 代码仓库的目录结构，而是任何 Agent 框架都必须回答的问题清单。读完之后，你评估任何一个 Agent 框架（LangGraph、Claude Agent SDK、OpenAI Agents SDK……）时，都可以拿这五问去逐一对照。

## 二、总览：一个循环、四层包、五个问题

**本章结论：pi 是一个四层的 monorepo，层与层单向依赖；上文的五个问题分别由不同的层回答。**

```
┌─────────────────────────────────────────────────────┐
│  pi-coding-agent   产品层：CLI/TUI、会话管理、压缩、  │
│                    扩展体系、四种运行模式             │
├──────────────────────────────┬──────────────────────┤
│  pi-agent-core               │  pi-tui              │
│  Agent 运行时：执行循环、     │  终端 UI 库：         │
│  工具调用、事件流、状态管理    │  差分渲染、组件系统    │
├──────────────────────────────┴──────────────────────┤
│  pi-ai   统一模型层：30+ 服务商、流式抽象、           │
│          成本核算、上下文防溢出                       │
└─────────────────────────────────────────────────────┘
```

- **pi-ai**（`packages/ai`）回答"怎么接模型"：统一的消息模型、流式事件、认证解析、token 与成本核算。
- **pi-agent-core**（`packages/agent`）回答"怎么执行"：Agent 循环、工具调用管线、事件订阅、steering/follow-up 队列。
- **pi-coding-agent**（`packages/coding-agent`）回答"怎么记忆""怎么扩展"和产品层的"怎么可靠可控"：会话树、压缩、扩展/技能/模板/主题、信任模型、四种运行模式。
- **pi-tui**（`packages/tui`）是支撑终端体验的渲染库（差分渲染、无闪烁同步输出），不在本文展开。

一个值得先记住的架构事实：pi 内置的交互模式、打印模式、RPC 模式**本身就是其 SDK 的消费者**——产品层没有任何私有通道，第三方用 SDK 能做到的事和官方 CLI 完全等价。这是"可扩展性"不是口号而是架构约束的第一个证据。

## 三、第一问·怎么执行：Agent 循环

**本章结论：pi 的执行引擎是一个约 800 行代码的双层循环——内层处理"模型响应 → 工具执行 → 用户插话"，外层处理排队的后续任务；所有状态变化都以事件流的形式对外广播，UI、持久化、扩展都只是事件的订阅者。**

### 3.1 回合（turn）：执行的基本单位

pi 对"一步"的定义很干净：**一个回合 = 一次大模型调用 + 该次响应触发的全部工具执行**。用户发出一个请求后，循环会跑一个或多个回合，直到模型的响应里不再包含工具调用（源码：`packages/agent/src/agent-loop.ts` 中的 `runLoop`）。

```
用户消息 → ┌ 回合 1：模型响应（含工具调用）→ 执行工具 → 结果回填
           ├ 回合 2：模型看到工具结果，继续响应（可能再调工具）
           └ 回合 N：模型给出纯文本答复，无工具调用 → 循环结束
```

内层循环每个回合结束后会检查 **steering 队列**（用户在 Agent 干活时插入的新指令），有则注入后继续；内层循环彻底结束后，外层循环检查 **follow-up 队列**（用户排队的后续任务），有则再启动一轮内层循环。这个双队列设计是 pi 人机协同体验的基础，第八章会与 LangGraph 的 interrupt 机制对照。

### 3.2 事件流：一切消费者都是订阅者

循环运行时对外发出一条有严格顺序保证的事件流：`agent_start` → `turn_start` → `message_start/update/end`（消息级，含逐字流式增量）→ `tool_execution_start/update/end`（工具级）→ `turn_end` → `agent_end`。

这个设计的产品意义在于：**终端 UI 的每一帧渲染、会话文件的每一次落盘、扩展的每一次拦截，消费的是同一条事件流**。pi 保证事件订阅者按注册顺序被逐个等待执行完毕（awaited），这意味着"持久化完成"可以成为下一阶段开始的屏障——牺牲一点吞吐，换来状态一致性。

### 3.3 工具调用管线：校验、拦截、并行、回填

模型请求调用工具后，每个调用经过一条五段管线（`agent-loop.ts` 中 `prepareToolCall` → `execute` → `finalize`）：

1. **参数校验**——工具用 TypeBox 声明 JSON Schema，参数先过校验（并有一个 `prepareArguments` 前置钩子，用来兼容不同模型的"手误"，例如某些模型把数组参数发成了 JSON 字符串）；
2. **前置拦截**——`beforeToolCall` 钩子可以直接阻止执行并给出理由，这是权限门禁的挂载点；
3. **执行**——默认**并行**执行同一批工具调用；但只要批次中有任何一个工具声明自己必须串行，整批都降级为串行（安全优先于吞吐）。对同一文件的并发写入由一个按文件路径排队的互斥队列保护；
4. **后置改写**——`afterToolCall` 钩子可以改写结果内容；
5. **回填**——工具结果作为消息进入上下文。执行完成事件按"实际完成顺序"发出（UI 可即时反馈），但落盘的结果消息严格按"模型请求顺序"排列（存档确定性）。

两个细节体现了 pi 对失败的严谨态度：其一，如果模型响应因输出 token 上限被截断（stopReason 为 length），**这条消息里所有工具调用一律作废不执行**——因为流式解析器会对截断的 JSON 做"尽力抢救"，抢救出的参数可能通过校验却语义残缺，执行它比失败更危险；其二，工具结果分为 `content`（给模型看的文本）和 `details`（给 UI 渲染的结构化数据，如 diff）两个通道，后者永远不进提示词，不占上下文。

### 3.4 错误即值：失败被编码成数据而非异常

pi 的模型调用层有一条贯穿性契约：**一旦请求发出，任何失败都不允许抛异常，必须编码为一条带 `stopReason: "error"` 或 `"aborted"` 的正常助手消息**，连同已经生成的部分内容和已产生的费用一起返回。被中止的消息是合法的上下文条目，可以在其基础上继续（`continue()`）。

这对产品意味着：网络闪断、限流、用户按下 Esc，都不会让会话进入"损坏"状态——它们只是历史里一条标记了原因的消息，重试、续写、放弃都是用户的自由选择而非工程补救。

### 3.5 一次请求的完整旅程（端到端追踪）

把前面的机制串起来，看用户输入"把配置文件里的超时改成 30 秒"之后系统内部发生的事：

1. **输入层**：交互模式先检查这是不是斜杠命令或技能调用；都不是，则作为用户消息进入循环。若 Agent 正忙，这条消息进入 steering 队列等待回合间隙。
2. **上下文组装**：会话树从当前叶子回溯到根（若途中遇到压缩节点则改用"摘要 + 近期消息"），配置节点折叠出当前模型与工具集，系统提示按当前活跃工具重新拼装。
3. **消息转换**：内部消息类型（含 UI 专用的通知、bash 执行记录等）经 `convertToLlm` 过滤转换成模型只认识的 user/assistant/toolResult 三种角色——**内部表达与模型协议是两层，中间有一道显式的转换边界**（`packages/agent/src/types.ts`）。
4. **模型调用**：pi-ai 解析认证（存储凭据优先于环境变量，OAuth 过期自动刷新）、按模型的 API 形态组装请求、钳制输出上限、打上缓存标记，发出流式请求。每个流式增量既作为事件推给 UI 逐字渲染，也在内存里累积成完整消息。
5. **工具执行**：模型响应说要调 `read` 和 `edit`。两个调用经校验、拦截钩子后并行执行（同文件的写入自动排队）；每个结果按 50KB/2000 行截断后回填上下文，并作为条目追加进会话树。
6. **循环与收尾**：带着工具结果再次调用模型，模型确认修改完成、给出纯文本总结，无新工具调用——循环退出前检查 steering 与 follow-up 队列，都为空则发出 `agent_end`。页脚的 token 用量、缓存命中率与费用在整个过程中逐条实时更新。

值得注意的是这条链路上每个环节都有扩展的挂载点：第 1 步的 `input` 事件、第 2 步的 `before_agent_start`（改系统提示）与 `context`（改消息）、第 4 步的 `before_provider_request`（改原始请求体）、第 5 步的 `tool_call`/`tool_result`。这就是"内核固定、变化外推"的具体形态。

## 四、第二问·怎么接模型：统一模型层

**本章结论：pi-ai 用"API 形态"与"服务商"两级抽象，把 30 多家模型服务归一到约 10 种协议实现之下；模型与对话上下文都是纯数据，因此"中途换模型继续聊"是一个序列化问题而非架构问题。**

### 4.1 两级抽象：~10 种 API 形态承载 30+ 服务商

pi-ai 观察到一个行业事实：服务商有几十家，但 API 的"形状"只有少数几种（Anthropic Messages、OpenAI Completions、OpenAI Responses、Google Generative AI、Bedrock Converse、Mistral Conversations 等，共约 10 种，见 `packages/ai/src/api/`）。因此：

- **API 实现**负责协议：怎么组装请求体、怎么解析流式响应；
- **服务商（provider）**只是"目录 + 认证 + 指到某种 API 形态"的组合——GitHub Copilot 同时代理 Anthropic 形态和 OpenAI 形态的模型，就声明两个映射即可。

每个模型是一条纯数据记录：`{ id, api, provider, baseUrl, contextWindow, maxTokens, cost, reasoning, input, ... }`，含分档价格（$/百万 token，区分输入/输出/缓存读/缓存写）。模型目录由脚本从 models.dev 等公开源生成并做完整性校验，**只收录支持工具调用的模型**——这是一个 Agent 框架的自我定位声明。

### 4.2 三大归一化难题

**思考/推理归一**。pi 定义了统一的 7 级思考梯度（off/minimal/low/medium/high/xhigh/max），再逐服务商翻译：Anthropic 走思考 token 预算，OpenAI 系走 `reasoning_effort`——而 OpenAI 兼容生态里光"怎么开思考"就有 11 种方言（DeepSeek、Qwen、ZAI、Together……各不相同），pi 用每模型的映射表逐一适配。产品启示：**"思考深度"这个用户旋钮的背后，是框架替你消化掉的碎片化**。

**跨模型重放**。思考内容带有服务商的加密签名，换模型后签名失效。pi 的策略是：同模型重放原样保留；跨模型时思考降级为普通文本、加密块直接丢弃、超长工具调用 ID 规范化；孤儿工具调用（有调用无结果）自动补一条"未提供结果"的错误结果。于是"上一半用 Claude、下一半换 GPT"开箱即用。

**提示缓存**。pi 默认开启短时缓存（`cacheRetention: "short"`），并按服务商翻译成各自的机制（Anthropic 的 cache_control 断点、OpenAI 的 prompt_cache_key、Bedrock 的 cachePoint），会话 ID 同时用于缓存亲和路由。缓存读写量和费用逐条消息实时核算，直接显示在界面页脚——**成本可观测是一等公民**。

### 4.3 上下文防溢出：一个被认真对待的脏问题

上下文超限是 Agent 最常见的故障，而各家的报错方式五花八门。pi 维护了一个 **24 种正则模式**的溢出识别库（外加排除误报的白名单，因为 Bedrock 把限流也说成"Too many tokens"），还处理两类根本不报错的情况：静默溢出（z.ai）和零输出的 length 停止（Xiaomi）。识别到溢出后触发自动压缩并重试一次（详见第五章）。发起请求前，输出上限会按"上下文窗口 − 已用估算 − 4096 安全余量"自动钳制，思考预算再向下调整以保证**至少留 1024 个 token 给正式回答**——避免"想了半天、一个字没说"的极端体验。

## 五、第三问·怎么记忆：状态与上下文管理

**本章结论：pi 把会话建模为一棵只增不删的树，把"上下文超限"处理为在树上追加一条摘要节点——完整历史永不丢失，发给模型的窗口按需重建。**

### 5.1 会话即树：原地分支，配置也是节点

每个会话是一个 JSONL 文件（`~/.pi/agent/sessions/` 下按工作目录归档），每行一个条目，条目之间用 `id/parentId` 连成树（`packages/coding-agent/src/core/session-manager.ts`）。当前对话位置是树上的一个"叶子"。

三个由此自然涌现的产品能力值得注意：

- **原地分支**：在 `/tree` 界面选中历史上任何一条用户消息，即可从那里长出新分支重新来过——不复制文件、不丢弃旧分支，两条时间线共存于一棵树；
- **配置即历史**：换模型、调思考等级、增删工具都会作为条目写进树里，于是"切回某个旧分支"会自动还原当时的模型与工具配置——不需要额外的配置快照机制；
- **分支摘要**：跨分支切换时，pi 会把被离开的分支压成一条摘要节点带到新位置，避免"切个分支就失忆"。

### 5.2 自动压缩：阈值、切点与迭代摘要

当上下文估算超过"窗口 − 16384 预留 token"时触发自动压缩（也可用 `/compact` 手动触发，或由溢出错误兜底触发）。算法（`packages/coding-agent/src/core/compaction/compaction.ts`）：

1. 从最新消息向回走，累计到约 20000 token（`keepRecentTokens` 默认值）处找切点——**切点永远不落在工具结果上**，保证工具调用与其结果不被拆散；
2. 切点之前的历史交给大模型压成一份**固定结构**的摘要（目标/约束与偏好/进度[已完成·进行中·受阻]/关键决策/后续步骤/关键上下文），并要求"保留精确的文件路径、函数名与报错信息"；
3. 若已有旧摘要，则采用"更新式"提示词做迭代合并（PRESERVE/ADD/UPDATE 规则），而不是每次从头总结；
4. 压缩期间读过/改过的文件清单被抽取出来、**跨多次压缩累积传递**——Agent 不会忘记自己动过哪些文件；
5. 摘要作为一条压缩节点追加到树上；下次请求的上下文 = 摘要 + 切点之后的近期消息。

若单个回合本身就超过保留预算（例如一次跑了几十个工具调用），切点会落在回合中间，pi 会为该回合的前半段单独生成一份"回合上下文"摘要并合并——这个"split turn"细节说明压缩不是可糊弄的边角，而是被当作核心路径打磨的。

token 估算刻意用廉价的启发式（字符数 ÷ 4，图片按 4800 字符计），但会锚定最近一次服务商返回的真实用量、只估算其后的增量——测量与估算混合，避免引入笨重的分词器依赖。

配套的还有工具输出的强制截断纪律：单次工具输出上限 50KB 或 2000 行（先到为准），bash 完整输出溢出到临时文件并告知路径。文档用了罕见的强硬措辞："工具**必须**截断输出"——因为不截断的输出会连锁引发上下文溢出、压缩失败与模型性能劣化。

## 六、第四问·怎么扩展：自扩展体系

**本章结论：pi 的扩展性不是"提供了插件接口"，而是一个闭环——极简内核留出全部空间，四类资源类型接住全部需求，而系统提示里内嵌的自身文档让运行其中的模型可以读手册、为用户现场编写扩展。这是"自扩展（self-extensible）"的确切含义。**

### 6.1 极简的起点：4 个工具、169 行系统提示

默认交给模型的工具只有 4 个：`read`、`write`、`edit`、`bash`（内置共 8 个，grep/find/ls/powershell 需显式开启）。整个默认系统提示由一个 169 行的源文件（`packages/coding-agent/src/core/system-prompt.ts`）拼装：一句身份设定、每个工具一行说明、按当前工具集动态计算的几条准则、项目上下文文件（AGENTS.md/CLAUDE.md，向上逐级目录合并加载）、技能索引、当前工作目录。没有长篇行为规范，没有几千 token 的说明书。

其中最与众不同的一段，是把 **pi 自身的 README、docs/ 目录与 79 个示例扩展的绝对路径**写进了系统提示，并附路由表（问扩展读 extensions.md、问主题读 themes.md……）。每份定制化文档的第一行都是同一句话："pi 能创建扩展。让它为你的场景写一个。"——**Agent 的首要扩展作者不是开发者社区，而是 Agent 自己**。用户说"我想要个危险命令确认弹窗"，pi 读自己的文档，现场写出扩展文件，`/reload` 热加载生效。

### 6.2 四类资源 + 打包分发

**扩展（Extensions）**是 TypeScript 模块，通过 jiti 免编译直接加载，能力面最大：约 40 个生命周期事件（会话启停、每次模型请求前后、每次工具调用前后、压缩前后、分支切换前后……），可注册新工具与斜杠命令、拦截并否决工具调用、改写系统提示与上下文、替换编辑器/页脚/整个界面组件（官方示例里有人用它在终端里跑 Doom）。权限门禁、Git 检查点、计划模式、子 Agent——别家内置的功能，在 pi 全是几十到几百行的示例扩展。

尤其值得产品经理注意的是**内置工具的可替换性**：八个内置工具与扩展工具共用同一个注册类型，扩展注册同名工具即完成覆盖，且渲染逻辑按槽位继承（只想加日志时可以保留原有的语法高亮渲染）。工具的底层操作层（读写、执行）也是可注入接口——官方示例据此实现了"工具在远程 SSH 主机 / 沙箱 / 微虚拟机里执行、界面留在本地"的三种形态。换句话说，**从"换一个按钮的颜色"到"把整个执行环境搬进虚拟机"，用的是同一套扩展机制**。

**技能（Skills）**实现了 Agent Skills 开放标准，核心机制是**渐进披露（progressive disclosure）**：启动时只把每个技能的名字和一句描述注入系统提示（一个 XML 索引块），模型判断任务匹配时才用 `read` 工具加载完整的 SKILL.md。一百个技能的常驻成本只是一百行索引——这是上下文经济学的教科书示范。pi 还明确支持直接挂载 Claude Code、Codex 的技能目录，跨 harness 复用。

**提示模板**是带参数替换的 Markdown 文件，文件名即斜杠命令；**主题**是 51 个颜色 token 的 JSON。四类资源都遵循同一套发现路径（全局目录 / 项目目录 / 包 / 设置 / 命令行），并可打包为 **Pi Package** 经 npm 或 git 分发安装。

一个具体例子可以说明扩展的表达力密度。下面这段不到十行的代码就是一个完整的危险命令门禁：

```typescript
export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("危险操作", "允许执行 rm -rf 吗？");
      if (!ok) return { block: true, reason: "用户拒绝" };
    }
  });
}
```

把它保存到 `~/.pi/agent/extensions/` 下即自动发现、`/reload` 即生效——而这段代码本身就可以由 pi 替用户写出。另一个体现深度的机制是**动态工具加载**：扩展可以注册上百个工具但只保持少数活跃，由一个"加载器工具"按需激活；在支持的模型上（Anthropic 的 tool_reference、OpenAI 的 tool search），新工具的定义会锚定在对话中途的激活点上，而不是插入提示词前缀——**从而不打破已建立的提示缓存**。工具管理与成本优化在这里被设计成了同一件事。

### 6.3 信任模型：自由的代价与边界

扩展拥有完整系统权限，pi 对此毫不讳言（文档原话："扩展执行任意代码……安装第三方包前请审阅源码"）。工程上的守门机制是**两阶段加载**：启动时先只加载全局与命令行指定的扩展，让它们有机会处理"是否信任本项目"的决策事件；项目本地的设置、扩展、技能必须在项目被信任之后才加载。至于运行沙箱，pi 的立场写在安全文档里：**进程内的半吊子沙箱容易被误解为安全边界，真正的隔离必须来自操作系统或容器/虚拟机**——所以 pi 提供的是容器化指南（Docker、微虚拟机 Gondolin），而非内置弹窗。

## 七、第五问·怎么可靠可控：与 LangGraph 的对照

**本章结论：LangGraph 用"图 + 检查点"这一显式状态机模型换取精确的控制与恢复能力；pi 用"循环 + 会话树 + 钩子"以更少的概念达成同类能力的大部分，并正在通过一份持久执行规范补齐最后一块。对照三大特性可以精确看清两种设计哲学的取舍。**

如果你从 LangGraph 走来，最需要的是一张术语映射表：LangGraph 的 thread 对应 pi 的会话文件；checkpointer 对应 SessionManager 的 JSONL 树；time travel 对应 `/tree` 原地分支；interrupt 对应 steering 队列与工具拦截；Store（跨线程记忆）对应 pi 的"显式文件"哲学。下面逐项展开。

### 7.1 Human-in-the-loop：中断点建在哪里

LangGraph 的做法是在图里显式设置中断——`interrupt()` 暂停执行、把控制权交还调用方，人审批后用 `Command(resume=...)` 恢复；中断点是图结构的一部分。

pi 把人的介入拆成了**三个不同时机的机制**，全部内建于循环而非由业务方建模：

- **steering（转向）**：Agent 正在执行时，用户随时输入新指令，按 Enter 进入 steering 队列——当前回合的工具调用会执行完毕（不撕裂进行中的工作），新指令在下一次模型调用前注入。这解决了"看它跑偏了想纠正，又不想按停重来"的高频场景；
- **follow-up（追加）**：Alt+Enter 把消息排到"全部干完之后"，相当于任务队列；Esc 则是硬中止，且排队消息会退回编辑器不丢失；
- **工具调用审批**：`tool_call` 扩展事件可拦截任意工具调用，弹出确认对话（`ctx.ui.confirm`）、静默放行或直接否决——相当于 LangGraph 里"在工具节点前加审批中断"的模式，但审批策略是用户侧扩展而非内核功能，可以按团队的安全要求任意定制（官方示例：对 `rm -rf`、sudo 弹窗，对 `.env` 写入直接拒绝）。

取舍很清晰：LangGraph 能在**图上任意节点**设中断，粒度更细、适合复杂审批流；pi 的介入点固定在"回合间"与"工具调用前后"两处，但换来了零建模成本——用户不需要理解图就能获得完整的插话、排队、审批能力。

### 7.2 持久化：线程级与跨线程

**线程级**。LangGraph 用 checkpointer 在每个超步后保存图状态快照，同一 thread_id 下可恢复、可回放、可从任意历史检查点分叉（time travel）。pi 的对应物就是会话树本身：每条消息、每次配置变更实时追加落盘，`pi -c` 继续最近会话、`/resume` 选择历史会话、`/tree` 从任意历史节点分叉、`/fork` 与 `/clone` 派生新会话文件。值得强调的是等价性：**LangGraph 的 time travel 需要理解"检查点 + 重放"，pi 的树分支就是文件里天然的数据结构**——回放即"从叶子走到根"。存储后端同样可插拔（JSONL 默认、SQLite、内存，共用一套一致性测试套件）。

**跨线程**。LangGraph 提供 Store 接口做跨 thread 的长期记忆（按命名空间存取、可语义检索）。pi 没有等价的内置键值记忆——这是刻意的：pi 的哲学是**跨会话状态应当是用户可见的显式文件**——项目约定写进 AGENTS.md（每个会话自动加载）、可复用能力沉淀为技能、偏好进 settings.json、待办用 TODO.md。此外扩展可以通过 `appendEntry` 把自定义状态写进会话树随会话持久化。对产品经理的启示：pi 把"记忆"从系统特性重新定义为**内容资产**——可审阅、可版本控制、可团队共享；代价是没有开箱即用的自动语义记忆，需要时得装包或自建。

### 7.3 持久化执行：崩溃之后还能继续吗

这是三项对照中差距最实、也最能看出 pi 演进方向的一项。

LangGraph 的 durable execution 提供三档持久化模式，配合确定性重放，让长任务可以在进程崩溃、部署重启后从最近检查点无感续跑。

pi **当前**的可恢复性由四层机制叠加而成：

1. 会话实时落盘——崩溃后 `pi -c` 恢复会话，完整历史都在，但"当时跑到一半的那个回合"需要用户再按一次继续；
2. 自动重试——模型调用失败默认重试 3 次（2s/4s/8s 指数退避），限流、超载、网络错误自动消化，配额耗尽类错误则识别为不可重试、立即上浮；
3. `continue()` 语义——错误与中止消息是合法上下文，从断点续写是一等操作；
4. 溢出自愈——上下文溢出错误触发压缩后自动重试一次被中止的回合。

而 pi 的**下一步**已经以完整规范的形式写在 `packages/agent/docs/harness.md`（近 3000 行，API 骨架已进主干，实现进行中）：一个以"写一次不可变的条目树 + 单写者操作日志 + 崩溃恢复归约器"为核心的持久运行时。其中几个设计点即使只作为思想实验也值得产品经理了解：每个外部效果（模型请求、工具执行）都包在"记录意图 → 执行 → 记录结算"的三明治里，ID 在执行前预留，因此崩溃在任意时刻都能明确判断"这个工具跑了没有"；工具需声明自己可否安全重放（`replay: "never" | "safe"`），不可重放的中断工具会得到一条合成的错误结果而不是被偷偷重跑（想象崩溃发生在 `rm` 执行中途）；恢复逻辑**拒绝修复损坏状态而非猜测续跑**——12 类日志损坏被枚举检测，宁可停机也不静默错乱。这与 LangGraph"确定性重放"的思路殊途同归，但把"哪些效果绝不能重放"提到了契约层面。

### 7.4 小结：何时选图，何时选循环

| 特性 | LangGraph | pi |
|---|---|---|
| 控制流 | 显式图（节点/边），业务方建模 | 固定循环，变化推到数据与钩子 |
| Human-in-the-loop | 图上任意点 interrupt/resume | steering/follow-up 队列 + 工具拦截审批 |
| 线程级持久化 | checkpointer 快照 + time travel | JSONL 会话树，分支即数据结构 |
| 跨线程记忆 | Store 接口（可语义检索） | 显式文件（AGENTS.md/技能/设置）+ 扩展自存 |
| 持久化执行 | 三档持久化 + 确定性重放 | 落盘 + 重试 + 续写（今）；持久运行时规范（进行中） |

粗略的选型直觉：**流程本身是产品**（多角色审批流、严格 SLA 的编排、需要在任意节点暂停的合规场景）时，图模型的显式性是资产；**对话与工具使用是产品**（编码助手、研究助理、运维 copilot）时，pi 式"循环 + 树 + 钩子"用更少的概念覆盖了绝大多数需求，剩余的定制通过扩展补齐。

## 八、六个"不做"：设计哲学与产品启示

**本章结论：pi 的每个"不做"都不是能力缺失，而是"把决定权还给用户"的刻意选择；这背后有五条可以迁移到任何 AI 产品的设计启示。**

pi 的 README 用一节"Philosophy"逐条列出它拒绝内置的功能与替代路径：

- **不做 MCP**——用"CLI 工具 + README"配合技能机制达成同样目的（模型读文档、调命令行），需要 MCP 的用户装扩展即可；
- **不做子 Agent**——用 tmux 起多个 pi 实例，或装第三方包按自己的编排方式实现；
- **不做权限弹窗**——真隔离交给容器，轻确认交给扩展，安全策略应贴合各团队环境而非一刀切；
- **不做计划模式**——把计划写进文件，或装扩展（官方提供示例实现）；
- **不做内置待办**——理由只有四个字："它们会干扰模型"（they confuse models），用 TODO.md 即可；
- **不做后台 bash**——用 tmux，换取完全可观测与直接交互。

给 AI 产品经理的五条启示，也是全文的收束：

1. **功能做减法，能力做乘法**。每个内置功能都是所有用户被迫接受的决定；pi 证明了把功能变成"可选资源"后，核心可以小到 4 个工具，而能力上限反而更高。
2. **渐进披露是上下文经济学**。技能索引一行、正文按需加载的模式，本质是把上下文窗口当稀缺预算管理——这个思路适用于一切"给模型喂知识"的场景。
3. **失败要设计成数据**。错误即值、截断即作废、中止可续写——把失败纳入正常数据流的系统，才能把"出错后怎么办"从工程事故变成产品体验。
4. **会话是资产，不是缓存**。树结构、原地分支、可导出可分享，加上跨会话的显式文件记忆，pi 把对话历史做成了可运营的内容资产。
5. **让 Agent 参与自身产品的扩展**。把产品文档喂给运行其中的模型、让用户"说需求、得插件"，是 Agent 时代独有的产品杠杆——它把定制化的边际成本压到了接近一次对话。
